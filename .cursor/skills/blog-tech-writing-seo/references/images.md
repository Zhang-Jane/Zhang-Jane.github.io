# 配图选择与处理（Hexo / Butterfly）

本文档服务于本仓库 **`source/_posts/*.md` + Butterfly 主题** 的成文流程。思路参考社区里的公众号配图经验（[BND-1/wechat_article_skills · image-guidelines](https://github.com/BND-1/wechat_article_skills/blob/main/wechat-tech-writer/references/image-guidelines.md)），已按**静态博客资源路径、可访问性与 SEO**改写，**不是**原文搬运。

**标题层级与最小 Frontmatter**见 **[SKILL.md](../SKILL.md)**。**语气、成文流程、自检**见 [writing.md](writing.md)。

**当前约定**：**不使用 AI 生成图作为配图方案**（无工具链、无统一版权与风格约束）。本文档讲的是**实拍截图、官方图、授权素材**等「配图」；**不是** AI 文生图工作流。若日后启用再单独开文档说明。

---

## 配图用来做什么

- 打断长文、降低阅读疲劳（尤其手机端）
- 让「界面长什么样、步骤卡在哪」一眼可见
- 复杂流程用一张简单图比三段话更省事

---

## 优先用什么图

| 优先级 | 类型 | 说明 |
|--------|------|------|
| 高 | 真实界面截图 | 终端、IDE、浏览器、产品后台；字号清晰、关键区域可读 |
| 高 | 仓库/文档页截图 | GitHub 页面、官方文档关键段落（注意版权与合理使用） |
| 中 | 官方架构/流程图 | 优先用厂商公开图；元素过多时考虑裁剪或拆成两张 |
| 中 | 数据图 | 来源可靠、坐标与单位清楚；避免信息密度超过正文需要 |
| 低 | Logo / 标识 | 文首或品牌介绍处；用官方清晰 PNG/SVG，避免糊图 |

**尽量少用**：把大段正文再做成一张「纯文字长图」——除非版式有特殊设计；否则应用 Markdown 标题与列表呈现，利于检索与无障碍。

---

## 数量与分布（中文长文经验值）

篇幅与配图可大致对应（不必机械凑数）：

- 约 **1000–1500 字**：**2–4** 张
- **1500–2500 字**：**3–6** 张
- **2500 字以上**：**4–8** 张，按章节拆开

**分布**：尽量**每 2–4 个段落**有一张相关图；开篇若有一屏能概括主题的图，有利于首屏体验。避免十几段纯文字后突然连续堆五张图。

---

## 不推荐的图

- 分辨率过低、压缩到字都糊掉的截图
- 与段落论点无关的「装饰图」（凑数会分散注意力）
- 元素过多、字过小的「全景架构图」（普通读者看不清时等于无效）
- 明显侵权或未授权商用素材、带第三方大水印截图（除非在合理使用范围内且合规）

---

## 在本仓库里怎么放（Hexo）

**本仓库约定**：配图**不要长期依赖外链 URL**（易失效、加载不可控）。无论是截图还是网上下载的示意图，都应**保存为本地文件**，统一放在 **`source/images/`** 下。

1. **目录**：在 `source/images/` 下按主题建子目录，便于归类（与现有文章一致），例如 `source/images/kafka/`、`source/images/mysql/`。新专题请**新建子目录**，目录名建议**英文小写 + 连字符**，避免中文路径带来的兼容问题。
2. **文件名**：**英文 + 连字符**，如 `vscode-agent-panel.png`，避免空格与怪异符号；尽量**不要**用中文文件名（历史文章里可能有，新文优先英文）。
3. **正文引用**：`source/` 下静态资源会映射到站点根路径。文章在 `source/_posts/某篇.md` 时，常用**相对路径**指向图片（本站多篇已采用）：

```markdown
![VS Code 中 Agent 面板的区域说明](../images/agent-skills/vscode-agent-panel.png)

*图：Agent 相关入口在侧栏中的位置（示例说明）*
```

   也可写成根路径形式 `![说明](/images/agent-skills/vscode-agent-panel.png)`（与相对路径二选一，全篇统一即可）。

4. **`post_asset_folder`**：仓库 `_config.yml` 中若开启 `post_asset_folder: true`，可与「文章同名资源夹」配合使用；**本 Skill 仍以 `source/images/` 集中管理为主**，与现有 `../images/主题/…` 写法一致。

5. **`alt`**：写清「图里是什么」，自然带上与主题相关的词即可，**不要**堆砌关键词；兼顾读屏用户与图片失效时的替代文字。

6. **体积**：大图尽量压缩（如 WebP/适当 PNG）；Butterfly 常带懒加载，但仍应避免单张数 MB 的原图直传。

---

## 缺图时怎么办

- 在草稿或 PR 说明里标注：`[待补：某某界面截图]`，发版前补拍。
- 若暂时无法截图，可用**步骤列表 + 命令块**把过程写清楚，配图后补，**不要为了占位随意找无关网图**。

---

## 与「文末不堆资源表」一致

成稿面向站点读者时：**不要在文末单独做「配图 URL 清单」替代正文**；链接与说明应体现在**插图位置、`alt` 与必要的一句图注**里。编辑阶段若需在 issue/清单里跟踪素材，可在仓库外或 PR 描述中维护，**不必**进 `hexo g` 后的正文。

---

## 成文前配图自检

```
- [ ] 每张图有明确用途（不是凑数）
- [ ] 图片已下载到本地，放在 source/images/<主题>/ 下（勿长期裸链外站图）
- [ ] 文件名以英文为主；路径可被 Markdown 正确引用（../images/... 或 /images/...）
- [ ] alt 能单独读懂；图注（如有）简短
- [ ] 无 AI 生成图依赖（当前流程不支持）
- [ ] 长文段落间大致均衡配图，避免首屏以下大片纯文字
```
