## 为普通用户写作（语气与可读性）

**目标读者默认**：对技术好奇、未必有深厚背景的**普通用户**。优先「听得懂、用得上」，再谈专业深度；专业术语首次出现要用人话解释或打个比方。

**核心原则**：像和朋友聊天，不像产品说明书或论文摘要；避免「AI 腔」（元叙事、提纲式预告、空洞排比）。

- **术语**：新名词先给一句人话定义或类比，再展开；能不用缩写就不用，必须用时紧跟短解释。
- **顺序**：先讲「是什么」「为什么值得关心」，再讲「怎么做」；步骤用数字列表，对比用项目符号。
- **改写**：理解观点后用自己的话重写；可调整段落顺序；禁止整段照搬、只换几个词、或保留原文句式骨架。
- **段落**：每段 2–4 句为宜；尽量不超过约五行；重要结论可单独成段。
- **句子**：以短句为主；复杂意思拆成几句；避免单句过长（中文以一口气读完为准，忌堆从句）。
- **人称**：多用「你」「我们」，少用「用户」「读者」等疏离称呼。
- **互动**：适当用反问（如「你是否也遇到过……？」）或一两处带温度的表达（切忌滥用感叹与鸡汤）。
- **列表**：功能点、步骤、对比表适合用列表，方便扫读。
- **标题（中文技术科普向）**：`{吸引注意} + {核心关键词}`，避免纯 SEO 堆砌；emoji 仅在小标题中适度使用，勿刷屏。
- **开头（钩子，约 100–200 字）**：可从场景、问题或一个具体事实切入，让读者知道「今天读完能带走什么」。
- **主体推荐块结构**（可按文裁减）：是什么 → 能做什么 → 为什么选它/它解决什么痛 → 如何开始；每块配小标题、2–3 段文字，并尽量有**至少一个具体例子**。
- **结尾**：用 2–3 句收束要点，再加 1 句轻量行动建议（例如「你可以先试试……」）。**不要在文末单独罗列「参考文献/资料列表」**；官方文档、规范站点等在**正文叙述中自然嵌入链接**即可（见下文「引用与链接」）。

**引用与链接**

- 优先在相关句子中直接给出 [锚文本](URL)，让读者顺着读就能点。
- 避免在文章末尾集中贴一条「文献表」或「链接大全」代替正文引用；若需资源汇总，应写成短段落 + 内嵌链接，并说明各自用途。

**宜避免的「AI 腔」示例**

- 元提纲：「第一节将完整展开……第二节将区分……」——改为直接切入内容，或用一句口语交代结构即可。
- 空洞强调：「具有重要意义」「全方位赋能」——改为具体结果或场景。
- 机械连接：「此外」「综上所述」连用——改用更自然的承接或分段。

**可读性（与标题层级配合）**

- 每段约 2–4 句、尽量不超过约五行；步骤与结论多用列表。

## Frontmatter 字段说明

以下配合 [SKILL.md](../SKILL.md) 第二节的最小示例使用。

| 字段         | 建议                                                                   |
| ------------ | ---------------------------------------------------------------------- |
| `title`      | 主关键词靠前；避免夸张、虚假时效                                       |
| 固定链接     | 全站为 `post/:abbrlink.html`，短且稳定；勿依赖中文文件名当 URL         |
| `tags`       | 细粒度、可检索；同一概念固定一种写法                                   |
| `categories` | 与站点导航、专题一致                                                   |
| `updated`    | 大改时可写；否则可依赖 `_config.yml` 的 `updated_option`（如 `mtime`） |
| `abbrlink`   | **勿在编辑文章时由 AI 自动添加或补全**。短链由本仓库 `hexo-abbrlink` 在本地 `hexo g` / `hexo new` 时生成并可选写回；避免与既有文章冲突或覆盖用户已固定的链接。 |

**abbrlink 与 AI**：新建或修改 `source/_posts/*.md` 时，除非用户明确要求写入或修改 `abbrlink`，否则**不要**在 Frontmatter 中新增、猜测或复制其它文章的 `abbrlink`。

## 推荐成文流程（草稿 → 发布）

1. **定读者与收获**：这篇读完能带走一句什么话？（可与 [seo.md](seo.md) 里的搜索意图类型对齐）
2. **骨架**：文首钩子 → 是什么/为什么 → 怎么做 → 收束与一句行动建议（见上文「主体推荐块结构」）
3. **初稿**：先写全，再改；专有名词第一次出现用人话或类比
4. **事实与可复现**：命令、版本、环境由你核对；AI 草稿里标「待验证」的必须落地
5. **润色**：砍 AI 腔、拆长句、加内链；配图按 [images.md](images.md) 补或标 `[待补图]`
6. **发布前**：走本文「成文前自检」

## 大纲与段落节奏（实操）

- 每一节先问自己：**这一段是在回答哪一个问题？** 答不上来就合并或删掉。
- 同一屏幕内：**一段一个意思**；列表前后各留一句承上启下，避免「光秃秃列表」。
- 长文在文首用 **TL;DR**，条目与后文小标题尽量对应，方便跳读。

---

## 引用、转述与链接（操作层）

- 转述材料时**重写句式与顺序**，不要只换几个词（与上文「改写」一致）。
- 官方文档、规范在**正文句子里**用 [锚文本](URL) 链出去；**不在文末**堆「参考文献表」。

## AI 辅助写作（减少幻觉）

1. 约定读者水平与格式：**Hexo Markdown**、**无正文 H1**、正文仅用 `##` / `###`
2. 事实边界：仅基于用户提供的材料；不确定处标「待验证」
3. 要求输出「须由作者补充的一手清单」（环境、版本、耗时、失败案例）
4. 同时索要 TL;DR 与 1–2 版 Meta Description 备选
5. **成文后人工**：核对事实、跑通命令/代码、补个人经验
6. **abbrlink**：不自动添加；由作者在本地构建时交由 `hexo-abbrlink` 处理

**可复用 Prompt 示例**

- 作为技术博客编辑，根据下列要点写 Hexo 正文：【要点】。约束：主标题仅出现在 Frontmatter；正文 `##`/`###`；文首 TL;DR；融入关键词【主关键词】；预留「第一手经验」段落；附 1–2 条 Meta Description 建议。
- 作为 SEO 审阅：下列全文是否符合 Helpful Content 与 E-E-A-T，标出薄弱处与可执行的修改建议。

**成稿前通读**

- **删掉元提纲**（「本文将分三部分……」）、**删掉空洞形容词**，补上你自己的环境与踩坑。

## 成文前自检（可复制）

```
- [ ] title 唯一、可读、主关键词靠前，无标题党
- [ ] 正文无 `#` H1；`##`/`###` 层级连续
- [ ] tags / categories 利于专题内链
- [ ] 长文 TL;DR 与结论一致
- [ ] 至少 3–5 条站内相关内链，锚文本具体
- [ ] 图片 alt、路径符合 [images.md](images.md)；代码与引用可核对
- [ ] 含可验证的一手细节（环境、版本、踩坑等）
- [ ] 大改后考虑标注更新日期或依赖主题展示「更新于」
- [ ] 以解决问题为先，而非为 SEO 而 SEO
- [ ] 文末无「文献/链接大全」式罗列；资源已在正文用链接交代
- [ ] 除用户明确要求外，未添加或修改 `abbrlink`
```
