## 为普通用户写作（语气与可读性）

**目标读者默认**：对技术好奇、未必有深厚背景的**普通用户**。优先「听得懂、用得上」，再谈专业深度；专业术语首次出现要用人话解释或打个比方。

**核心原则**：像和朋友聊天，不像产品说明书或论文摘要；避免「AI 腔」（元叙事、提纲式预告、空洞排比）。

- **术语**：新名词先给一句人话定义或类比，再展开；能不用缩写就不用，必须用时紧跟短解释。
- **顺序**：先讲「是什么」「为什么值得关心」，再讲「怎么做」；步骤用数字列表，对比用项目符号。
- **改写**：理解观点后用自己的话重写；可调整段落顺序；禁止整段照搬、只换几个词、或保留原文句式骨架。
- **段落**：每段 2–4 句为宜；尽量不超过约五行；重要结论可单独成段。
- **句子**：以短句为主；复杂意思拆成几句；避免单句过长（中文以一口气读完为准，忌堆从句）。
- **人称**：面向读者的说明、步骤、轻量反问多用「你」「我们」，少用「用户」「读者」等疏离称呼；叙述**作者一手经验**、个人判断、踩坑与立场时用「我」，避免把本属作者实践的内容全程写成对「你」的指令。
- **经验的可复用叙事**：**把经验打包给智能体读**（见 [Agent Skills：AI 时代的可复用能力封装](https://zhang-jane.github.io/post/cd4fa45f.html)）与 OpenClaw 等体系中的 Skill 市场，是**同一思想在不同产品里的体现**：一边是通用 Agent Skills 规范与 IDE 生态，一边是 OpenClaw 系里的 Skill 市场——写综述或对比时，用「我」串起观察与取舍，再用内链展开，而不是只堆「你该如何」。
- **互动**：适当用反问（如「你是否也遇到过……？」）或一两处带温度的表达（切忌滥用感叹与鸡汤）。
- **列表**：功能点、步骤、对比表适合用列表，方便扫读。
- **标题（中文技术科普向）**：`{吸引注意} + {核心关键词}`，避免纯 SEO 堆砌；emoji 仅在小标题中适度使用，勿刷屏。
- **开头（钩子，约 100–200 字）**：可从场景、问题或一个具体事实切入，让读者知道「今天读完能带走什么」。
- **主体推荐块结构**（可按文裁减）：是什么 → 能做什么 → 为什么选它/它解决什么痛 → 如何开始；每块配小标题、2–3 段文字；技术向文章另见下文「**技术博客：事实、通俗、术语与案例**」。
- **结尾**：用一小节 **「核心要点」**（或起同样作用的结尾小节，项目符号或极短段落即可），**只复述本文已论证过的结论**，不引入新论点、不堆套话。**不要在文末单独罗列「参考文献/资料列表」**；官方文档、规范站点等在**正文叙述中自然嵌入链接**即可（见下文「引用与链接」）。

**引用与链接**

- 优先在相关句子中直接给出 [锚文本](URL)，让读者顺着读就能点。
- 除官方文档、规范、RFC 外，**技术博客**（本站或他站）可作观点、实践路径与产品对比的来源；句中交代「谁在什么语境下」、链接指向原文，与文档类引用同一套写法。
- 避免在文章末尾集中贴一条「文献表」或「链接大全」代替正文引用；若需资源汇总，应写成短段落 + 内嵌链接，并说明各自用途。

**宜避免的「AI 腔」示例**

- 元提纲：「第一节将完整展开……第二节将区分……」——改为直接切入内容，或用一句口语交代结构即可。
- 空洞强调：「具有重要意义」「全方位赋能」——改为具体结果或场景。
- 机械连接：「此外」「综上所述」连用——改用更自然的承接或分段。

**可读性（与标题层级配合）**

- 每段约 2–4 句、尽量不超过约五行；步骤与结论多用列表。

## 技术博客：事实、通俗、术语与案例（推荐风格）

面向**技术主题**（教程、原理、对比、踩坑记录等）时，在「为普通用户写作」的基础上，建议同时满足下面几条；与 SEO、内链等要求不冲突。

### 实事求是

- **结论有据**：性能数字、兼容性、「官方推荐」等说法尽量交代**依据**（文档版本、复现环境、测量方法）；拿不准就写「在我当前环境下」或标「待验证」，不替读者拍胸脯。
- **边界说清**：适用系统、语言/运行时版本、已知限制（deprecation、breaking change）写一句即可，避免把特例写成普遍真理。
- **一手与引用分清**：自己的操作步骤、报错与官方文档说明分开写，避免混在一起看起来像「我验证过」实则未验证。

### 通俗化讲解与专业词汇

- **先义后名**：先用一两句日常话说明**在解决什么问题**，再给出术语或 API 名；复杂机制可用「相当于……」「可以把它理解成……」搭桥。
- **缩写与专名**：首次出现建议 **中文全称或含义 + 英文缩写（如有）**，例如「内容分发网络（CDN，Content Delivery Network）」；后文可只用缩写。
- **注解写法**：括号短注、文内「即……」「也就是……」、或紧随其后的加粗定义句均可；**同一篇内同一术语只用一种固定写法**，避免一会儿全称一会儿别名。
- **避免假通俗**：比喻要能对应到真实行为（例如「快递分拣」对应请求路由），避免只为好玩而误导。

### 实战案例（1–3 个）

- **数量**：一般 **1–3 个**即可；短笔记可以 1 个，长文或对比类可到 3 个。忌堆满半文不切题的「示例」。
- **要短小可落地**：每个案例最好包含**目标一句 + 关键命令或代码片段 + 预期现象或注意点**；读者能照着做或能对照自己的报错。
- **与正文挂钩**：案例应直接服务上一节的结论（例如用一条命令验证「缓存是否命中」），而不是另起炉灶讲故事。
- **环境可复现**：至少点明 OS、工具/语言**大版本**（如 Node 20、Python 3.12）；需要网络或账号时写明，避免「你照做必失败」。

### 文末：简要总结核心内容

- **单独成段或小节**（如 `## 核心要点`），**3–7 条列表**或一段极短文字，覆盖：本文主旨、关键结论、适用/不适用场景各一句（若适用）。
- **只总结正文已写内容**，不写「未来可研究……」式凑字；不与开头钩子简单重复，而是**压缩后的可带走清单**。

## Frontmatter 字段说明

以下配合 [SKILL.md](../SKILL.md) 第二节的最小示例使用。

| 字段         | 建议                                                                                                                                                           |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `title`      | 主关键词靠前；避免夸张、虚假时效                                                                                                                               |
| 固定链接     | 全站为 `post/:abbrlink.html`，短且稳定；勿依赖中文文件名当 URL                                                                                                 |
| `tags`       | 细粒度、可检索；同一概念固定一种写法                                                                                                                           |
| `categories` | 与站点导航、专题一致                                                                                                                                           |
| `updated`    | 大改时可写；否则可依赖 `_config.yml` 的 `updated_option`（如 `mtime`）                                                                                         |
| `abbrlink`   | **勿在编辑文章时由 AI 自动添加或补全**。短链由本仓库 `hexo-abbrlink` 在本地 `hexo g` / `hexo new` 时生成并可选写回；避免与既有文章冲突或覆盖用户已固定的链接。 |

**abbrlink 与 AI**：新建或修改 `source/_posts/*.md` 时，除非用户明确要求写入或修改 `abbrlink`，否则**不要**在 Frontmatter 中新增、猜测或复制其它文章的 `abbrlink`。

## 推荐成文流程（草稿 → 发布）

1. **定读者与收获**：这篇读完能带走一句什么话？（可与 [seo.md](seo.md) 里的搜索意图类型对齐）
2. **骨架**：文首钩子 → 是什么/为什么 → 怎么做 → **1–3 个实战案例** → **文末简要总结**（建议用小标题「核心要点」，见上文「技术博客：事实、通俗、术语与案例」与「主体推荐块结构」）
3. **初稿**：先写全，再改；专有名词第一次出现用人话、括号注或类比
4. **事实与可复现**：命令、版本、环境由你核对；AI 草稿里标「待验证」的必须落地；结论与边界分开写
5. **润色**：砍 AI 腔、拆长句、加内链；配图按 [images.md](images.md) 补或标 `[待补图]`
6. **发布前**：走本文「成文前自检」

## 大纲与段落节奏（实操）

- 每一节先问自己：**这一段是在回答哪一个问题？** 答不上来就合并或删掉。
- 同一屏幕内：**一段一个意思**；列表前后各留一句承上启下，避免「光秃秃列表」。
- 长文在文首条目与后文小标题尽量对应，方便跳读。

---

## 引用、转述与链接（操作层）

- 转述材料时**重写句式与顺序**，不要只换几个词（与上文「改写」一致）。
- 官方文档、规范、**博文**在**正文句子里**用 [锚文本](URL) 链出去；**不在文末**堆「参考文献表」。

## AI 辅助写作（减少幻觉）

1. 约定读者水平与格式：**Hexo Markdown**、**无正文 H1**、正文仅用 `##` / `###`
2. 事实边界：仅基于用户提供的材料；不确定处标「待验证」
3. 要求输出「须由作者补充的一手清单」（环境、版本、耗时、失败案例）
4. 同时索取 1–2 版 Meta Description 备选
5. **成文后人工**：核对事实、跑通命令/代码、补个人经验
6. **abbrlink**：不自动添加；由作者在本地构建时交由 `hexo-abbrlink` 处理

**可复用 Prompt 示例**

- 作为技术博客编辑，根据下列要点写 Hexo 正文：【要点】。约束：主标题仅出现在 Frontmatter；正文 `##`/`###`；文首钩子（约 100–200 字）；融入关键词【主关键词】；**实事求是、术语有解释；含 1–3 个可复现实战案例；文末用「核心要点」一小节作简要总结**；预留「第一手经验」段落；附 1–2 条 Meta Description 建议。
- 作为 SEO 审阅：下列全文是否符合 Helpful Content 与 E-E-A-T，标出薄弱处与可执行的修改建议。

**成稿前通读**

- **删掉元提纲**（「本文将分三部分……」）、**删掉空洞形容词**，补上你自己的环境与踩坑。

## 成文前自检（可复制）

```
- [ ] title 唯一、可读、主关键词靠前，无标题党
- [ ] 正文无 `#` H1；`##`/`###` 层级连续
- [ ] tags / categories 利于专题内链
- [ ] 长文文首钩子与文末「核心要点」一致、不跑题
- [ ] 技术向：结论有依据或已标明「待验证」/个人环境；重要限制与版本有交代
- [ ] 技术向：关键术语首次出现有短定义或注解；缩写规范统一
- [ ] 技术向：含 1–3 个与正文挂钩的实战案例（含环境/版本要点为佳）
- [ ] 文末有简要总结（核心结论与适用边界），无空话、无新论点
- [ ] 至少 3–5 条站内相关内链，锚文本具体
- [ ] 图片 alt、路径符合 [images.md](images.md)；代码与引用可核对
- [ ] 含可验证的一手细节（环境、版本、踩坑等）
- [ ] 大改后考虑标注更新日期或依赖主题展示「更新于」
- [ ] 以解决问题为先，而非为 SEO 而 SEO
- [ ] 文末无「文献/链接大全」式罗列；资源已在正文用链接交代
- [ ] 除用户明确要求外，未添加或修改 `abbrlink`
```
